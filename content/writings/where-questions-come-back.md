# 能并行还不够，我更在意问题回到哪

昨天在 Hacker News 上刷到 Claude Code 团队的 Boris Cherny 解释 [Projects](https://code.claude.com/docs/en/claude-projects) 里 coordinator 的动机。他说得很直白：模型越能干，人们就越容易同时开出好几路 Agent；活是能并行了，可自己的注意力也被一并拆碎，那种感觉很糟糕。

我的判断很简单。一个人用 AI 把生意跑起来，真正稀缺的不是又能多开几路干活的 Agent，而是有一个入口，把做完的结果和必须我拍板的问题，收回到同一处。

## 并行之后，先碎掉的是人

Claude Code 的 Projects 不是这几天才有的。今年 9 月 17 日，Anthropic 把旧的项目文件夹改成了一场[持续的对话](https://claude.com/resources/articles/projects-redesigned)：你在一个入口交代目标，它把活分给并行的线程，再把结果拼回来。官方的说法是，你像在给一位参谋长交代任务。

这两天它再次出现在 [Hacker News](https://news.ycombinator.com/item?id=50492141) 上，Boris 自己来答问题。他写，团队观察到，人们一旦习惯 Claude Code，就会再开一条线程去做下一件事；模型更聪明、token 更省、云端还能跑得更久之后，这种「multi-Claude」会越来越常见。活确实能同时推进，可时间一长，切换上下文、盯住每一路进展，会让人觉得产品不够用。

与此同时，他也说，不是所有工作都该被并行。有时你就是要盯住一件事，来回打磨，并不想把注意力切到别处。单线程的专注仍然重要。

他们给出的办法，不是再加一个更忙的仪表盘，而是一个入口。你跟项目的 coordinator 说话，由它把活派给线程；线程并行跑，进展和问题再冒回主对话。你也可以随时跳进某一路，做深一点的事。Boris 后来补了一句，这样用下来，他不再觉得自己在脑子里来回跳。

官方文档把分工写得很清楚。项目是一场长期对话，Claude 在里面当 coordinator：它决定什么该开新线程，跟踪它启动过的每一路，但只看见线程汇报回来的东西，而不是每一步。线程才是干活的人，各自有自己的上下文。Overview 会标出哪些已经做完、哪些 PR 待审、哪一路在等你回答。没有这个项目时，协调工作是你自己在做：给每一路重复背景，再挨个回去看谁做完了、谁卡住了。

我在意的不是云端会话或手机遥控这些功能点。我在意的是它承认了一件很普通的事：Agent 一多，人会先变成传话的人。

## 我缺的不是更多手，是一个收件处

我自己这套写作、短帖和发布流程，已经够让人想再开几路了。选题、成稿、封面、飞书、站点，路径差不多，输入却每天不同。贸易那边的询盘、样品、交货，也常常和内容工作叠在同一天。最容易产生的幻觉是：既然它能并行，我就该同时把这些都铺开，自己在中间当调度。

短时间里，这会有一种很强的效率感。过一会儿你就会发现，真正被并行的不是工作，是你的注意力。这个线程问一个用词，那个线程卡在一张图，第三个已经把一稿写完等你看。你不再是在做判断，而是在给每一路做即时回复。

我自己就有过这种下午。一边改封面，一边等表格回写，一边又开一扇窗去核对一个出处。每一路都在工作，可我只是在几扇窗口之间点头。看起来忙，其实没有多做出一个判断。

所以我更想要的，不是「再多开几个 Agent」，而是一个收件处。活可以分头去干，但只有两类东西应该回到我面前：做完、等我看的结果；以及必须由我拍板的问题。其余过程，我不需要实时围观。能写进流程的，就不要再变成一场需要我盯着的聊天。

这也是我给自己设的界限。汇总不能代替底稿。coordinator 把话说回来之后，我还是要能打开那一路，看见它改过什么、依据是什么，尤其是要发出去的文字和要上线的改动。发布、付款、删除这类动作，仍然走原来的门：先问我，再放行。入口是为了保护注意力，不是为了把决定权再交出去。

我也不会为了证明自己够新，就把所有事情拆成十路同时跑。官方文档写得很清楚，Projects 会更快用完同一套用量额度。对一个人和一套自己的系统来说，开得越多，并不自动等于走得越稳。能回到同一处的问题，才值得我在那天打开。

所以，我羡慕的不是它能同时派出多少线程。我要的是更窄的一句话：活可以分头干，问题得回到同一处。
