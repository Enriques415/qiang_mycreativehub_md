11 月 11 日，AWS 放出一个叫 [AWS Emulator](https://aws.amazon.com/blogs/aws/test-your-applications-against-aws-locally-with-aws-emulator/) 的东西。装在本机，两百多个 AWS 服务跟着下来，438 个 API 模型，Rust 写的，不用账号，不联网，不产生账单。代码在 [GitHub](https://github.com/aws/aws-emulator) 上，CC0 公有领域，连提交历史一起公开。

新闻标题都盯着另一句话：整个代码库没有一行是人写的，也没有一行是人审的。项目负责人 Matthew Goldberg 在发布文里写得很直白——模拟器完全由自主 agent 写成，团队没写、也没审过任何一行代码。

我看到这条时先是想「这早晚会来」。但真正把我钉住的不是「没人写」，而是它把「哪些还不对」也一起交了出来。

## 它先把缺口摊在桌上

这一版对外的说明里，有一串不太像发布会该有的东西。每个服务的保真度按「k of n」公布，五十条测试过四十条就写四十；没实现的操作直接返 501，让测试立刻红，不要静悄悄地糊过去；仓库里有两个目录，一个叫 `things-that-now-work`，一个叫 `things-that-do-not-work`，后者是公开的、还在长的欠账清单。

然后是我读到之后停了一会儿的那句：它不按 AWS 的方式评估 IAM 和资源策略。所以，一个真云会拒绝的请求，在这里可能成功。

这句话的分量比「没人审代码」重得多。一个不准的副本，最坏的情况不是它报错，是它放行。

## 我熟悉这种失败

我自己的自动化里，我怕的从来不是它崩。崩了我立刻知道，日志里一行红字，五分钟修好。

我怕的是它安静地做成了。文章写完了，封面出图了，表格写进去了，一条流水线从头跑到尾一个错没报。然后隔两天我打开一看：标题里多出一个我没打算写的主张，表格那一列压根不是我想要的字段，封面上的字排歪了三度。它没有失败，它只是没对。

以前我把这种时刻归成「模型还不够好」。这次读完 AWS 那份说明，我觉得归类归错了。问题不在它写不出来，问题在我给它的验收条件太软——软到「跑通了」就算过。

## 功劳不在会写，在参照物

这套东西能成立，靠的不是 agent 有多能写。靠的是那批保真测试，而它们的来源被钉死了：每条测试先对真云跑一遍，跑通了才被收进测试集，之后才可以在没有云的地方反复重放。

顺序很重要。不是「agent 写了代码，我们看看像不像」，是「真云先定义了什么叫对，然后所有人都对着同一个东西交作业」。

三个 agent 团队——写测试的、找差异提单子的、一次修一个单子的——分工之所以能转起来，是因为它们争的不是审美，是那几千条能重放的判据。合并门禁里排着编译、编码规范、专门做对抗审查的安全 agent、保真回归，任何一项不过就打回去重做。据说每天修掉几千个单子，几百个 agent 同时在改同一个仓库。没有那道门，Goldberg 自己说，他不敢信这些东西。

同一天配套的那篇文章里，还有个更干净的对照。Werner Vogels 和 Swami Sivasubramanian 写，Swami 想让 Kiro 重建二十年前那套 Paxos 锁服务的复制引擎，他盯了四个晚上，出来的一直是不能用的东西。后来他给了精确的规格，加一个能本地跑起来的测试台，两个小时就成了。

变的不是模型。变的是它终于有个地方，能立刻知道自己错了。

## 涂色本是给反馈，不是给限制

Goldberg 用了一个我没想到的比喻。他小时候画恐龙，因为手不稳，把全班那张大纸画坏了，同学冲他吼。他说他今年对 agent 发火的次数多到自己都不愿承认，但两边都不是恶意，是能力不够。后来他和伴侣一起涂色本，发现被给一块已经画好边界的区域其实很舒服——你知道更大的那张图会自己长出来。所以他写：agent 也需要涂色本。

这个比喻很容易被读成「给 agent 设限」，我不这么理解。他们在早期版本里干过一件事：为了支持 Lambda，agent 自己从零写了一个 Python 解释器。没人拦着，也没人告诉它有现成的库能用。这不是它们想造反，是它们不知道边界外面已经有答案。所谓涂色本，是给它一个能当场判断「这一步走没走对」的框，不是把它的手捆起来。

放到一个人身上，这条尤其扎。我一个人做事，最缺的从来不是产能，是没有人站在旁边说「这样不对」。

## 所以我把验收写小一点

我不会去装那个模拟器，我用不上两百个 AWS 服务。但它给了我一个能抄的做法，而且今天就能抄。

我给自己那几条每天跑的流程，加的不是更多指令，是更硬的验收。指令越写越长，是我在替它做判断；验收写得具体，是它自己就能判断。比如一篇稿子写完，不算「通读一遍看顺不顺」，而是问：标题里有没有出现我没打算写的第二个主张，每个引用链接打不打得开，字数落没落在区间里。这些都能机器判，判不过就不算完。

还有一条更难的，是学会写下「这个不管」。「这份校验不检查事实是否正确」，「这个副本不代表真实环境」。AWS 那句「别拿它测安全性」写得一点都不体面，可正是这句话让它敢被用。

## 最后

副本永远是副本。它跑得再顺，上线前还得去真的那边跑一遍。这不叫谨慎，这叫流程里本来就该有的那一步。

我这周真正改的一件事，是把「它跑通了」从验收清单里划掉了。
