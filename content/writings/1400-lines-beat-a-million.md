今天写这个题，是因为 11 月 23 日一个叫 Shoebox 的开源项目上了 Hacker News。它做的事情不新鲜——让一个主 Agent 把任务分给一群子 Agent 去做。新鲜的是它的做法：没有数据库，没有网关，没有自己发明的 Agent 循环，只用 Markdown 文件和 Docker 容器，代码约 1400 行。而它的对手们，动辄上百万行。

我关心这个，不是因为「又一个 Agent 框架」。是因为它戳中了一个独立做事的人最容易掉进去的坑：把工具搭得比生意还复杂。

## 它在比什么

Shoebox 的核心设定很朴素：每个 Agent 就是一个文件夹，里面放它自己的指令、工具和 Docker 镜像。任务是这个文件夹里的一个 Markdown 文件，你把文件从 `todo` 挪到 `in-progress`、再挪到 `done` 或 `blocked`，状态就跟着变了。就这么简单。

它用的是 Pi 当底层 harness，主 Agent 接到任务后，为每个子任务开一个独立的 Docker 容器去跑。跑完了或者卡住了，主 Agent 收到通知，再报给你。你这边可以继续聊别的，不用盯着。所有 Agent 的定义、技能、记忆，都用 git 做版本管理——改错了，`git revert` 就回来了。

数字上的对比更直白。Shoebox 约 1400 行非空源码（不算 Pi 这类依赖），闲置内存不到 100 MB。作为对照，OpenClaw 大约 540 万行、闲置 970 MB；Hermes Agent 约 160 万行、450 MB。三个数量级的差距。

先别急着信这些数字——这是作者自己公布、媒体转述的口径，没有独立跑过分。但就算打个对折，方向也站得住：一大块所谓的「Agent 平台」，重量并不来自它做的事，而来自它给自己加的壳。

## 复杂度是债，不是能力

一个人做生意，最容易犯的错是把「大厂怎么干」当成「我应该怎么干」。看别人上多 Agent 编排、上工作流引擎、上可观测平台，就觉得自己也该配一套。结果生意还没跑起来，先花两周调框架。

Shoebox 这类项目提醒的是另一件事：**系统的价值，取决于你能不能在它出问题时看懂它。** 1400 行代码，一个人一个下午能读完；540 万行，你连从哪读起都不知道。当你只有一个人，没有运维团队，可读性就是可用性。

这跟你选什么模型、用什么 Agent 无关。真正决定你能不能长期跑下去的，是这套东西出了 bug 的时候，你是「打开文件夹改一行 Markdown」，还是「在某个自己写的调度器里找三个小时的竞态条件」。

我自己的判断标准现在很简单：**一个工具，如果我需要专门记它的规则才能用对，它就是债。** 好的系统应该符合常识——文件夹就是分类，挪文件就是改状态，git 提交就是存档。Shoebox 把状态管理放进文件夹结构里，这不是简陋，是把「看一眼就懂」当成设计目标。

## 什么时候这套够用，什么时候不够

说清楚边界，不然就是另一种吹捧。

Shoebox 够用的场景，恰恰是一个人：几个到十几个并行任务，每个任务相互隔离，主 Agent 负责分配和回收。它的看板就是文件夹，进度一目了然，出问题把容器删了重跑。这对你这种「内容 + 代码 + 贸易」多线并行、但每条线都不复杂的情况，几乎刚好。

它不够用的地方也很明确：任务之间有复杂的依赖和共享状态时要上真正的调度器；Telegram 入口目前只能跟主 Agent 直接聊天，子 Agent 的编排能力还没接上；需要企业级权限、审计、高可用的时候，那 540 万行不是白写的。

所以结论不是「轻量永远赢」，而是：**先用最轻的，等它真的撑不住了再加。** 大部分独立工作的人，永远到不了需要加的那天。你以为自己在做工程，其实是在给一个还没存在的规模预付成本。

## 一个人的系统，应该能被一个人看懂

这两年我越来越确信一件事：AI 把「搭系统」的门槛降得太低了，低到你一天能搭出三个自动化流程。门槛低的结果不是人人都有好系统，而是人人都在囤积自己看不懂的系统。

真正稀缺的不是搭建能力，是克制——是你能忍住不加那个「以后可能用得上」的模块。Shoebox 用 1400 行证明，把一件事做对，本来就不需要那么多代码。多出来的部分，多半是在解决「别人以为你会遇到的问题」。

我现在给自己定了一条线：任何一个自动化，如果我不能在五分钟内说清它在干什么、数据存哪、出错了去哪找，我就不上线。一个人跑生意，最贵的不是算力，是注意力。把系统做轻，省下来的不是内存，是你明天还愿意打开它的意愿。
