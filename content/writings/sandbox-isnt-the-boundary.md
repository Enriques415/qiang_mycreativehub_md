11 月 16 日，Simon Willison 在 Prime Radiant 的博客里发了 [External sandboxes for coding agents](https://blog.primeradiant.com/external-sandboxes-for-coding-agents/)。一起放出的，还有三套能跑起来的原型，以及给 Claude Code、Codex 和 Pi 的对接说明。

他要解决的问题，我自己也每天碰到。Coding Agent 会搞错。搞错的时候，凡是它读得到、改得到的东西，都可能被弄坏，或者被带出去。常见的应对就两条：要么把整台电脑和外网都交给它，再祈祷别出事；要么每一步都要我点头。后一种他写得很狠：慢，而且很快就会点到麻木，问题还没看清，手已经先批准了。

我的判断也很简单。一个人用 AI 把生意跑起来，真正要看的不是它终于能自己跑命令，而是这些命令到底碰得到什么。沙箱开了，不等于边界已经画好。

## 外部沙箱，先把 Agent 留在外面

他们把这套做法叫做 external sandboxes，外部沙箱。名字容易让人以为沙箱在电脑之外，其实不是。沙箱和 Agent 都可以留在同一台机器上；所谓「外部」，是指沙箱在 Agent 之外。

这一点是他们刻意选的。另一种做法，是把 Agent 本身塞进沙箱里跑，比如 Fly 的 Sprites。他们试过，最后没有走这条路。原因写得很清楚：Agent 如果待在沙箱里面，就可能改到自己，或改到自己所处的环境；把 Agent 留在外面，命令再送进去，边界才更容易检查。

具体做起来并不花哨。Agent 还在你的 Mac 上跑，Claude Code、Codex、Pi 都是如此。真正执行的命令，进到一个 Linux 环境里。那个环境默认只能看到你挂载进去的目录，也可以分成只读或可写；默认没有外网，要访问的话，得经过一个代理，而且只能访问你允许的主机。他们还做了密钥替换：沙箱里的程序可以用占位符去请求某个 API，真正的密钥由宿主机上的代理在出站时补上，不进 Agent 的视野，也不进沙箱。

三套原型走的是不同的技术，但对外是同一套协议：一套用 Node.js 和 WebAssembly 跑 Alpine Linux，一套包住 Apple Containers，一套用 Microsoft 的 Quicksand 加 QEMU。项目主页在 [GitHub](https://github.com/prime-radiant-inc/external-sandbox)。对我来说，值钱的不是又多了三个可以试用的工具，而是他们把「能跑命令」和「能碰到什么」拆开了。

Anthropic 和 OpenAI 当然也在自己的产品里做了安全层。Willison 提到，Claude Code 的 auto mode，以及 Codex 的 auto-review，都会再用一层模型，判断这一步大概能不能继续。他承认这些检查看起来管用，但那是特定产品里的功能，仍然取决于模型有没有判断对。沙箱不一样：它是一道不依赖任何模型判断的保护。尤其当你想换成更便宜、更小、甚至能在本地跑的模型时，这一点更要紧——这些模型更容易出错，也更容易被提示词注入钻空子。

## 开了沙箱，并不等于它碰不到主机

真正让我停下来的，是他们写在用法里的那句限制。

Claude Code 接到这套沙箱时，送进去的只是 Bash 命令。它自带的 Read 和 Edit，仍然直接作用在你的 Mac 上。也就是说，挂载规则限制的是命令能碰哪里，并不限制它读文件、改文件。Codex 会把进程和文件系统操作（包括 `apply_patch`）送进沙箱；Pi 则用扩展把 bash、read、write、edit 这些工具都换成沙箱里的版本，并且可以用 `--no-builtin-tools`，避免扩展没加载成功时，工具又掉回主机。

同样叫「接上了沙箱」，三种工具画出的边界并不一样。如果我只是看到 Claude Code 的命令在 Linux 里执行，就以为自己的项目目录、相邻文件夹、甚至家目录里的密钥都已经隔开了，那是自己骗自己。

他们自己也把话说在前面。这些还是实验性的原型，没有审计到可以托付敏感工作的程度。可写的挂载仍然允许 Agent 破坏那个目录里的任何东西，所以要放在版本控制之下，能只读就不要可写。沙箱里跑的是 Linux，项目里为 macOS 装好的 `node_modules` 或 `.venv`，到里面可能还得重装。

密钥替换也不是万能的。代理可以把 GitHub token 留在宿主机，但若你允许访问的那个服务把密钥原样写回响应里，它还是可能露出来。他们的建议很具体：只对你信任的服务开这条规则，并且把方法和路径收窄。

这些限制并不让这篇文章变得没意义。恰恰相反，它们提醒我：安全功能的名字，常常比实际边界更大。一个人同时跑内容、代码和生意，机器上不会只有当前这个仓库。客户资料、别的项目、支付和平台的密钥，往往就在旁边几个目录里。Agent 要干活，就必须碰当前这份项目；但「让它干活」和「让它够得到我这台电脑上的其他东西」，不应该被当成同一件事。

## 我要留下的，是可检查的边界

我不会因为这三套原型还没完成审计，就觉得可以继续把整台电脑交给它。更不会把「每次都点允许」当成严谨——那种严谨，坚持不了几个晚上。

我更想留下的，是检查边界的习惯。先问这次任务需要哪些目录、要不要外网、密钥是不是必须出现在对话或环境变量里。能把命令送进一个只看得到项目目录的环境，就不要默认打开家目录；能让密钥停在代理这一侧，就不要把它贴进提示词。若工具宣称已经「在沙箱里跑」，我还得再看一眼：读和写，是不是也走同一条边界。

不是禁止它执行。是执行之前，先看清楚它碰得到什么。
